Extensions and modeling

  • Coupled resources: simultaneous pickup/delivery, selected values, cumulative costs and affine dependencies in the physical-graph labeling engine.

  • Multiple time windows: disjoint service-start domains for scalar pricing resources.

  • Multi-pricing: shared masters, multiple route families, and assignment branching.

  • Finite column imports: original-vector patterns and multiplicity constraints.

  • P-step CVRP: compact p-step LP relaxation.

  • Electric-vehicle routing: charging models, schedule replay, and current limitations.

  • Interior-point solver: native LP backend, interfaces, and implementation details.

  • Column elimination (CE): decision-diagram route relaxation and refinement.

Generic mixed-integer master solve highs::solve_integer Not exposed directly Not exposed HiGHS

The vrptw and cvrp routing tree uses one pricing network. For models with multiple route families, use the multi-pricing interface, including its CLI and Python APIs and assignment tree. Its supported branching families and solve limitations differ from the single-network routing tree.

Root Optimal means the LP relaxation converged. Tree Optimal means the integer routing gap closed within the configured tolerances. A feasible restricted-column solution supplies an incumbent; its objective alone does not prove a lower bound for the full routing problem.

Rust module organization

Core modules implement graphs, labeling, pricing, cuts, enumeration and the master. master::mp coordinates one master with multiple pricing subproblems and belongs to the core master framework. Rust callers can also use master::mp::solve_master for original master variables with no pricing subproblems.

Module Purpose
extensions::hgs Hybrid Genetic Search and primal heuristics
extensions::ipm Native interior-point LP backend
extensions::evrp Electric-vehicle routing models and charging schedules
extensions::pstep P-step CVRP LP with parallel bucket pricing and reference enumeration
master::mp Shared rows, per-subproblem multiplicities and node lifecycle

extensions groups algorithms and specialized models in the same crate; it does not imply runtime plugins or new build features. Existing baldes::hgs, baldes::ipm, baldes::evrp and master::networks paths remain compatibility re-exports. New Rust code should use the module paths above. CLI JSON fields and Python names such as NetworkProblem and solve_networks stay compatible.
