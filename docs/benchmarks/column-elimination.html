Column elimination model reductions

Measured on 2026-10-21. The comparison baseline is the working implementation after bulk LP loading, local feasibility pruning and batched refinement were added. The candidate adds resource propagation, graph compaction, exact-state sharing and a capacity-indexed ng relaxation. Both solve the continuous elementary route LP with Clp; integer solution costs are not the comparison target.

Reference audit

The reference implementation was inspected at vrptwdecisiondiagram.cpp and vrptwddsolver.cpp.

Reference mechanism Result in this implementation
generateNewStateRelaxation, compileNgRoute: load, time and ng visit memory Added capacity-indexed states with two-customer ng memory for bounded integer-demand CVRP cases; general instances use forward resource bounds and layered states. Initial time bucketing remains unimplemented.
addNode, separateRoute: state reuse and outgoing exact-feasibility checks Added exact state sharing by location, complete visited set and bitwise load/time; new states filter every outgoing action.
fixArcs: forward/backward reduced-cost distances and an incumbent cutoff Not copied into the continuous LP mode. An integer incumbent cutoff does not justify setting every positive fractional use of an expensive arc to zero.
findMergeNodesReducedCost: relaxed dominance merging above a reduced-cost threshold Not enabled; this differs from sharing equal exact states and can weaken the relaxation.
Flow-model dual starts; Lagrangian/subgradient solving; RCC/SRC separation and primal heuristics Remain separate future work. These require additional backend/state mapping or a stronger, explicitly different optimization mode.

The candidate also physically removes unreachable nodes and disabled arcs, so dead rows/columns no longer enter subsequent LPs or occupy persistent diagram budgets. Every retained internal node lies on a root-to-sink path.

Preservation rules

Forward load/time labels are independent minima, not a claim that one path attains both. A transition is removed only if an optimistic label already violates a resource constraint. A reverse connectivity pass removes dead regions. The same floating-point operation order as route replay is used for each forward resource update; no triangle inequality is assumed.

Exact refinement uses the complete visited set, including zero-demand customers. Bitwise active-resource matching avoids approximate state merging. Arrival time is omitted only when every deadline is infinite and a monotone upper-bound calculation proves all elementary route times remain finite. The preflight accounts for reused states and filtered successors, so a refinement that does not fit leaves the diagram untouched.

The capacity initial model is used automatically for at least 20 customers when demands are positive bounded integers and every window upper bound is infinite. Demand GCD scaling is exact. Scaled capacity must be at most 4n, and conservative dense state/arc estimates must fit the requested budgets. Zero/fractional demand or finite windows use the general construction.

Reproduction

cargo build --release --features clp --bin baldes
# Preserve each binary before rebuilding the other implementation.
node scripts/benchmark_column_elimination.mjs baseline=/path/to/baseline reduced=/path/to/reduced

The script warms up both binaries, alternates their order between trials, and runs three trials per case. C101, R101, P-n16-k8 and its first ten customers have a ten-second budget. A-n32-k5 has thirty seconds because its capacity-indexed model needs a longer first LP solve. CE_BENCH_TIME, CE_BENCH_RUNS and CE_BENCH_OUT override the defaults. JSON reports under target/ce-reduction-benchmark/ include CPU/compiler metadata, binary hashes, individual wall times, solve statuses, bounds, sizes and iteration counts. Timeouts are compared by the last optimal bound, not by an asserted speedup.

C101 preserves its bound and reduces final graph size from 10,028 nodes / 438,238 arcs to 565 nodes / 16,351 arcs. It now needs one LP solve instead of two. A-n32-k5 is the remaining hard case. Its stronger initial capacity-state model has 5,025 nodes and 129,255 arcs, so its first LP solve is more expensive than that of the weaker layered model. At the thirty-second cutoff it has 5,119 nodes / 131,756 arcs and four LP calls, with three completed optimal LP solves. The retained bound is valid but does not establish LP convergence.

Parallel LP experiment

A diagnostic export of the candidate's initial A-n32-k5 diagram produced one fixed LP with 5,055 rows, 129,255 columns and 377,719 nonzeros. All thread configurations used the same saved MPS, with the same nonnegative variables, 1e12 default column bounds and fleet constraint as the Clp formulation. The snapshot is target/ce-reduction-benchmark/a32-initial.mps, SHA-256 cdd979061b51515b91357bb6da4d6f7a0a22c053b12f7ab5de6d84e211106b8c.

HiGHS 1.15.1 was measured with a twenty-second solve budget, three interleaved trials and a fresh process each time. Serial dual simplex used strategy 1; the parallel PAMI configurations used strategy 3 and concurrency 2 or 4. Native logs confirm the requested parallel solver and concurrency were used.

Threads Median HiGHS solve time Median process wall time Speedup vs serial HiGHS
1 13.14 s 13.332 s 1.00×
2 10.99 s 11.175 s 1.20×
4 6.59 s 6.771 s 1.99×

All nine solves finished optimal at objective 741.3618123, matching the candidate's initial Clp relaxation within reporting precision. This is an LP-only experiment: it predates the optional --solver highs --threads N CE integration, and no end-to-end speedup follows from this snapshot alone. Clp remains the default backend. The speedup compares supported serial/parallel HiGHS configurations, not HiGHS against Clp. It does not establish a universal thread count or justify threading the much smaller route-check loop. HiGHS also describes its parallel dual simplex as memory-bound.

HiPO was attempted but this installed HiGHS build lacks its required amd, blas, metis and rcm features, so no HiPO timing is reported.

node scripts/benchmark_ce_lp_threads.mjs target/ce-reduction-benchmark/a32-initial.mps

Raw solver logs, options and measurements are saved under target/ce-lp-threads/. The script accepts any provided MPS and records unavailable solver builds explicitly.

All-CPU worker selection

The CE CLI now supports --solver highs --threads 0, resolving zero to all CPUs available to the process, and preserves explicit positive worker limits. On this host that requests 32 worker threads. The linked HiGHS 1.15.1 reports an eight-task limit for PAMI simplex; the constructor queries this option limit and configures the maximum supported concurrency. Logs and JSON expose both counts. No global scheduler reset is performed.

Three further fixed-LP trials compared worker pools above the earlier four-thread setting. Both requested eight PAMI tasks and all six solves finished optimal at the same objective 741.3618123:

Worker threads Simplex task limit Median LP solve time
8 8 5.69 s
32 8 7.12 s

Using all logical CPUs did not improve this LP. Eight workers were faster in this comparison, and the larger pool provided no additional PAMI concurrency. These measurements support retaining explicit thread controls rather than treating the available CPU count as universally fastest. Raw records are under target/ce-lp-full-cores/.

End-to-end CLI smoke checks with --solver highs --threads 0 reported 32 workers / eight maximum simplex tasks. C101 converged to 828.936867, and P-n16-k8 converged to 441.000000. A-n32-k5 reached bound 745.711111 at a thirty-second timeout (five LP calls, four completed optimal solves). These are functional integration checks, not a repeated end-to-end speedup study.

R201 time-window diagram

Validation

cargo test -p baldes --offline --lib extensions::column_elimination --features clp
cargo test -p baldes --offline --lib --bin baldes --features clp,highs thread
cargo check -p baldes --offline --bin baldes --features clp
cargo clippy -p baldes --offline --lib --bin baldes --features clp,highs

Nineteen focused tests cover independent elementary-route enumeration, fractional LP agreement, directed nonmetric travel, forbidden arcs, zero/fractional demands, floating-point boundaries, exact state sharing, compaction, atomic limits and the automatic capacity-state mode. Additional thread-option tests read the actual native settings, verify clone preservation and reject invalid CLI combinations before input loading. CLI smoke runs check serial and all-CPU HiGHS solving and the JSON thread fields.

The remaining large-model costs include repeated LP solves and eventual growth of exact visit-history states. Capacity states can produce a stronger initial bound while taking longer to solve their first LP. These changes do not establish an integer optimum or remove worst-case exponential growth.
