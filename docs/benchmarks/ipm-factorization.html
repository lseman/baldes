IPM factorization: cached assembly and lower-triangle updates

This comparison measures the native Rust IPM before and after the assembly-map, workspace, and dense-kernel changes. The baseline already includes the tree/node parallel controls. These are BALDES-to-BALDES measurements, not a comparison against HiGHS timings.

Changes

  • Compute CSC-to-front scatter positions and child-to-parent row maps during symbolic analysis. Share immutable maps across solver clones.
  • Retain dense scratch, pivot permutations, multiplier vectors, and output column capacity across Newton steps. Reset scratch when the symbolic plan changes; solver clones start with independent empty scratch.
  • Update the contiguous lower triangle and read symmetric pivot candidates from that triangle. Avoid mirroring the trailing matrix after every pivot. The previous full-matrix kernel remains an independent test oracle.
  • Batch tree work over retained scratch buffers. Nested node work uses the same bounded Rayon pool; no workspace lock is held during nested execution.
  • Recycle consumed Schur buffers through a size-binned pool, capped at 8 MiB per solver. The limit covers spare buffers, not live contributions or factors. Releasing consumed contributions avoids retaining every clique on deep trees.
  • Preserve the serial up-looking fast path and release its old compressed factor before allocating the next output.

The dense update is still a rank-1/rank-2 kernel. Blocked panel factorization, relaxed supernodes, and dependency-driven subtree scheduling remain future work.

Method

Measured on an AMD Ryzen 9 9950X (16 cores, 32 logical CPUs), Linux x86_64, with rustc 1.97.1 / LLVM 22.1.6. Both binaries use the repository's release profile (opt-level 3, thin LTO), the same expanded benchmark, and the same input and diagonal sequences. No compiler or other validation job ran during timing.

Each process performs one warmup and 30 measured refactorizations. Diagonals vary as 1 + iteration / repeats. Tables give the median of three independent process medians, with the range of those medians where shown. Baseline/candidate execution order alternates between repetitions. Setup, factorization, and solve timings are collected separately. One worker is used for off, four for both and choose; there is no CPU affinity pinning.

The dense-front fixture has 512 identity columns and one column touching all 512 rows. The forest has four independent 128-row components of that form; the unbalanced forest has components of sizes 32, 64, 128, and 256. The routing case is the captured r201_master.txt fixture. Every solve is checked against a known KKT witness, with maximum absolute solution error below 1e-8.

Interpretation and limits

Compare before/after within the same mode. A faster forced-parallel path can still be slower than the serial up-looking algorithm on a small sparse matrix. Choose retains that fast path when the structural heuristic finds insufficient work. Setup and solve costs should be included when judging end-to-end impact.

The synthetic fronts demonstrate dense-kernel and assembly behavior, not speedups for arbitrary routing instances. These measurements do not cover NUMA scaling, very deep elimination trees, or multiple simultaneous solver instances.

Provenance

The implementation was informed by inspection of HiPO's precomputed assembly indices and frontal storage reuse. The Rust kernel preserves this project's pivot policy and regularization rules.

Baseline source fingerprints (the worktree snapshot immediately before these optimizations, including the preceding parallel-control changes):
